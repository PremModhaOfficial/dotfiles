## 1. `caveman-help` prescribed a setting nothing reads

`caveman-help/SKILL.md:41-58` said "Configure Default Mode" via
`CAVEMAN_DEFAULT_MODE` and `~/.config/caveman/config.json`.

Real mechanism, verified: the resolver exists only in the caveman *repo*
(`src/hooks/caveman-config.js`: env → repo `.caveman/config.json` → user
`~/.config/caveman/config.json` → `caveman`), and only that repo's Claude Code
hook scripts and OpenCode plugin load it. Neither is installed here —
`rg -c caveman ~/.claude/settings.json` = none, no OpenCode caveman plugin — and
the installed `@caveman-ai/cli` bundle has no reader
(`rg -a CAVEMAN_DEFAULT_MODE` over the package: no match, rc=1;
`~/.config/caveman/config.json`: missing). On this host the mode is simply the
skill loaded: `/skill:caveman`, `/skill:ultracave`, `/skill:megacave`, or the
phrase. Nothing persists between sessions.

Fix: sync-owned card, so the text lives in `skills-overlay/caveman-help.sh` as a
third patch (plus the two existing ones), anchored on the old section with
`## Choosing the mode` as the drift marker. Proof: `rg -n '^## (Configure Default
Mode|Choosing the mode)' caveman-help/SKILL.md` → `41:## Choosing the mode`, and the
new section says plainly that exporting the variable changes nothing here.

Left alone deliberately: `ponytail-help/SKILL.md:53,58` (`PONYTAIL_DEFAULT_MODE`,
`~/.config/ponytail/config.json`) is the same shape but is not one of the six.

## 4. Overlay false pass — fixed as a class, not an instance

`tiger-style-review.sh` exited 0 on a missing anchor and still wrote
`.overlay-applied`, so the audit believed the patch landed. It was not alone:
15 of the 26 overlay scripts carried the same forward-only `patch()`.

Checked every overlay, 26 scripts:

- 5 already correct (`caveman`, `megacave`, `ponytail`, `tiger-style`,
  `ultracave`: `ensure_block`, drift 2, missing anchor 3, no marker);
- 15 false-pass (`ai-image-generation`, `caveman-help`, `caveman-review`,
  `cua-driver`, `ghostex-{agents,browser-use,cli,computer-use,help,manage-beads,visuals}`,
  `ponytail-gain`, `tiger-style-help`, `tiger-style-review`, host `paperclip`):
  the local `patch()` printed `anchor not found` then `sys.exit(0)`, and the
  script went on to `touch "$MARK"`. Their `no SKILL.md`, `cannot cd`,
  `mktemp failed` and `not writable` paths also exited 0;
- 6 have no anchor logic at all (`cavecrew`, `caveman-{commit,compress,discover,setup,stats}`).

Class fix, one implementation instead of 15 copies:
`~/dotfiles/jcode/overlay-lib.sh` now holds `patch()`. Missing anchor → exit 3;
drift (caller passed a `present` marker, section there but edited) → exit 2;
applied/already-applied → 0; the status is propagated (`[ "$rc" -eq 0 ] || exit
"$rc"`) so a failed patch cannot reach the marker. The lib is resolved from the
script's own directory *before* any `cd`, and a missing lib exits 3 rather than
falling through to the system `patch` (it did that once during this round and
returned 0 on garbage). The `refusing: not a <skill> skill dir` guards in
`cua-driver` and `paperclip` are now 3 as well — a refusal is not a pass.

`tiger-style-review.sh` also needed real work: its section text had drifted from
the live card (an older wording), so both patches were permanent "anchor not
found" warnings. Its two `NEW` blocks were rebuilt byte-for-byte from the live
card and the calls now pass `"## Comment voice"` / `"## Not this one"` drift
markers.

Proof for all 20 anchor overlays (`bash <script>` with `SKILL_DIR` on a fixture,
`CLONE` set):

## Two more fixes the pipeline forced

The first two real runs after wiring the transform ended `exit=1`, and the cause
was not the transform:

- `skills-cap.py`'s `SLASH` term regex stopped at the colon, so shortening a
  `/skill:<name>` description recorded the term `/skill` and dropped the name —
  its own check then reported `FAIL routing term gone: ponytail-gain:
  '/ponytail-gain'`. Fixed: `/(?:skill:)?[a-z0-9][a-z0-9-]{1,40}`, so the term
  and the kept text stay `/skill:<name>`.
- A sync writes bare text into `~/.agents/skills` while the vendored copy of the
  same skill under `~/.pi/agent/git/` is already rewritten, so the cap read two
  forms of one description, recorded terms from both, and failed on whichever
  copy it compared. Fixed by ordering: activation before the cap.
