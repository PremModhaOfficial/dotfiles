## The rule

1. **No state file → no floor.** First run records `count`, `fingerprint` and the
   file list, exits 0. That is the cold machine, the fresh checkout, and a tree
   someone emptied on purpose.
2. **Count below the recorded count → refusal, exit 1.** The message names both
   numbers, the previous fingerprint, and which skills are gone. State is not
   touched, so the next run still refuses.
3. **Count above the recorded count → one `WARN:`, exit 0, re-baseline.** Growth is
   an upgrade, a restored checkout, or a state left over from a wiped run.
4. **Same count, different fingerprint → silent re-baseline, exit 0.** Cards are
   rewritten every run by the overlays; content changes are normal and are recorded,
   not policed.
5. **The same tree in a different order → no warning.** The fingerprint is
   path+bytes, so a re-installed identical card cancels out (tested).
6. **Missing or unparsable state file → treated as no state.** A corrupt baseline
   can never brick a sync.
7. **`--rebaseline`** is the door for a shrink nobody wants to fail: it warns once
   and records the smaller tree.

Why only the shrink direction fails: no sync step here deletes installed cards.
`sync_dir` (`update-all.sh:487-502`) is `cp -R` into the destination with no
`--delete` and no prune; the only `rm -rf` in the updater is old run directories
(`update-all.sh:1179`). So a smaller tree is either a deliberate removal (the
operator says so with `--rebaseline`) or a bug, and nothing in the pipeline can
explain it.

State file, live machine after its first run (written before IT3-7's grammar landed;
the count is what matters, the fingerprint re-baselines silently on the next run):

Written by rename (`skills-activation.py:112`), so an interrupted run cannot leave a
half-written baseline that the next run reads as a shrink.

## Limits

- Phase granularity, not a whole `--skills-only` run: that `git pull`s five upstream
  repos into the sandbox first (`update-all.sh:504-556`) and proves nothing about this
  ticket. Composition (phases loop → `run_jobs` → overall exit) was read at
  `:1196-1218`, not exercised here; IT3-7 ran the live `--skills-only` path separately.
- Same count, truncated content is not caught: the fingerprint changes, the run
  re-baselines silently. Only file *loss* fails. Closing that would need a per-file
  size expectation, which this ticket did not ask for.
- Changes are in the `~/dotfiles` working tree, not committed: `jcode/skill_slash.py`,
  `jcode/skills-activation.py`, `jcode/update-all.sh` were already dirty from round 3,
  and `jcode/skills-lint.py` / `jcode/skills-activation.test.py` are untracked.
- The live `.agents/loop/` directory is dotfiles-untracked, as before.
